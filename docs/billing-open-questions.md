# Billing Open Questions — Host-on-Usenova

> **Status:** Open — no implementation until P0/P1 items are complete.
>
> This document tracks key design decisions that must be resolved before
> billing can be implemented for the Host-on-Usenova fleet path. Use this
> file (and PR/issue comments) to record decisions as they are made. Nothing
> here changes any existing code.
>
> Related: [docs/host-on-usenova.md](host-on-usenova.md) •

## Checklist

### 1. Who submits `create_escrow`?

- [ ] **Decision needed**

The Soroban `create_escrow` call transfers funds from the consumer's address
into the contract. The consumer must authorize the transaction, but the
_construction_ and _submission_ of that transaction is an open question.

**Options:**

| Option | Actor | Notes |
|--------|-------|-------|
| A | CLI | User signs and submits directly from their wallet. No secrets leave the client. |
| B | Control plane | Control plane builds the XDR and returns it; user signs off-band (e.g. wallet connect). |
| C | Separate wallet step | Dedicated wallet UI handles signing; the CLI triggers it via deep-link or callback. |

**Open sub-questions:**
- Where does the escrow ID come from? Generated by the control plane before
  the deploy command is enqueued, or by the CLI?
- Who holds the `provider` address (Usenova's receive address)? Hard-coded in
  the CLI, returned by the control plane, or stored in a config?
- What happens if `create_escrow` fails after a deploy command is already
  enqueued?

---

### 2. Refund behaviour if deployment fails

- [ ] **Decision needed**

The contract supports `refund(id)` which returns funds to the consumer. The
contract does **not** verify service delivery — that decision is made
off-chain. Who decides a deploy has failed and triggers the refund?

**Open sub-questions:**
- Does the control plane monitor deploy status and automatically construct a
  refund XDR for the user to sign?
- Is there a timeout? If the agent never reports back, when (and who) decides
  the deploy failed?
- Can the user self-serve the refund from the CLI (`nova billing refund
  <deploy-id>`)? If so, what access control prevents premature refunds?
- Does a partial deploy (container starts then immediately crashes) count as a
  failure for refund purposes?

---

### 3. Idle / ongoing pricing model

- [ ] **Decision needed**

The current escrow contract is amount-agnostic and models a single one-time
payment. Running services accrue ongoing cost.

**Options to decide between:**

| Model | Description | Escrow implications |
|-------|-------------|---------------------|
| Prepaid flat rate | User locks a fixed amount per deploy; releases after an agreed period. | One escrow per deploy; amount chosen upfront. |
| Prepaid time-based | User prepays for N hours; metered by the platform. | Single escrow; amount = hours × price. |
| Per-deploy (no idle) | Services are stateless; each deploy is a discrete job. | Simplest; maps cleanly to current contract. |
| Subscription | Monthly fee; escrow used as a deposit. | Escrow as deposit, separate billing cycle. |

**Open sub-questions:**
- If the user's prepaid balance runs out while a container is running, what
  happens? Graceful shutdown? Grace period?
- Does idle time (container running but receiving no traffic) cost the same as
  active time?
- Who is the `provider` address when there are multiple fleet machines? Is it
  a single Usenova treasury address or per-agent?

---

### 4. Prepaid vs per-deploy billing

- [ ] **Decision needed**

Closely related to question 3 but specifically about the payment UX:

**Prepaid (account balance):**
- User tops up a Usenova account; each deploy debits the balance.
- Usenova manages the Stellar escrow internally.
- Simpler UX; hides Stellar complexity from the user.

**Per-deploy (user holds escrow):**
- User submits a `create_escrow` for each deploy.
- User retains custody of funds until release.
- More transparent; user can self-refund on failure.
- More friction; requires the user to hold XLM/token.

**Open sub-questions:**
- Is the per-deploy model too much friction for non-crypto-native users?
- If prepaid, does Usenova need a custodial Stellar account per user, or a
  single treasury with off-chain accounting?
- Can both models coexist (prepaid for convenience, per-deploy for power
  users)?

---

### 5. Multi-tenant escrow IDs and collision avoidance

- [ ] **Decision needed**

The escrow contract uses a caller-supplied `u64` ID. In a multi-user fleet
there is no on-chain namespace per user.

**Open sub-questions:**
- Who generates the escrow ID? Control plane (UUID → uint64 hash), CLI, or
  user?
- How do we guarantee uniqueness across concurrent deploys from different
  users?
- Should the control plane maintain an escrow ID registry to detect collisions
  before submitting?

---

### 6. Release authorization and SLA enforcement

- [ ] **Decision needed**

Currently `release(id)` requires the **consumer** to authorize. For
Host-on-Usenova, the consumer (end user) may not be available or attentive
enough to sign the release after the service is delivered.

**Open sub-questions:**
- Do we add a co-authorization path to the escrow contract (consumer OR
  platform after a timeout)?
- Or do we keep the contract simple and handle SLA enforcement purely
  off-chain?
- What is the expected latency between "container healthy" and "release
  submitted"?

---

### 7. Mainnet readiness

- [ ] **Decision needed**

All payment flows currently target Stellar **testnet**. Mainnet requires:

- Formal security audit of `contracts/payment-escrow/`.
- Decision on which token(s) are accepted (XLM, USDC, other).
- Key management and HSM strategy for Usenova's provider address.
- Regulatory considerations (jurisdiction, KYC/AML if required).

This is explicitly a **non-goal for MVP** but decisions here constrain
earlier design choices (e.g., token address is hard-coded or configurable).
